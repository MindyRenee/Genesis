Module mmap_state 

Source
Expand description

Memory-mapped core state file.

This is the persistence layer for GenesisCoreState. It handles:

  • Creating a new state file on disk (zeroed, then initialised)
  • Opening an existing state file and mapping it into memory
  • Crash recovery: detecting corruption via magic, version, and checksum, and recovering when possible
  • Lock-free reads: readers get an owned copy of the state via a single volatile copy — no Rust reference to the mmap’d memory is ever created, so there is no aliasing with concurrent writers. A racing read may observe a torn snapshot; readers that cannot tolerate that take the flock-serialized read_consistent_locked path.
  • Serialized writes: writers are serialized by the in-process write_lock mutex and the cross-process flock; each publish is a single volatile copy of a fully-prepared stack state.
  • Synchronisation: sync() flushes dirty pages to disk so state survives a crash

§Why mmap instead of read/write?

On a 4.7 GB RAM machine, we can’t afford to hold copies of state in heap memory. With mmap, the OS manages paging — the ~3.4 KB state struct occupies a single page (4 KB), and the kernel keeps it cached or pages it out as needed. We get a direct pointer to the file’s contents with zero copy.

§Memory safety: why no &GenesisCoreState?

The mmap’d region is MAP_SHARED — it can be modified by another thread (via MmapState::modify) or another process at any time. Returning a Rust &GenesisCoreState from the mmap’d memory would be undefined behaviour: Rust’s aliasing rules forbid a & from coexisting with a &mut to the same bytes. The compiler is free to assume that a & reference’s pointee does not change, which could cause miscompilation when another thread writes through &mut.

Instead, the read API (MmapState::read and MmapState::read_consistent) performs volatile byte copies through raw pointers, returning an owned GenesisCoreState on the stack. Readers therefore create no reference to the mmap’d memory at all.

§The writer never forms a reference into the mapping

Every production write path — MmapState::modify and the open-time repairs/migrations — runs its mutation on a stack copy and publishes it with publish_stack (a single write_volatile). No & or &mut into the shared mapping is ever formed, so there is no aliasing with concurrent readers under Stacked/Tree Borrows: the old pattern (a &mut GenesisCoreState materialised into MAP_SHARED for the whole transaction, which Miri flagged and which only happened to survive because volatile loads are never dead) is gone.

Consequences, kept deliberately:

  • A panicking MmapState::modify closure only ever saw the stack copy, so the mapping needs no rollback — it was never touched.
  • read_volatile in the readers remains load-bearing: it stops the compiler eliding or merging the loads, it is not (and never was) what made concurrent access defined.
  • MmapState::state_mut was removed: it formed &mut references into MAP_SHARED memory with exclusivity left to the caller, and the only callers were tests that now use modify’s stack copy. No API may vend references into the mapping.

§File layout

offset 0:     GenesisCoreState (3480 bytes)
offset 3480:  (unused, padding to page boundary)

The state struct is 3480 bytes and the file is page-aligned, so the mapping is at least one page and the state sits at its start. (On a host with a 64 KiB page — aarch64, for instance — page_align_up expands the file to 64 KiB, not 4 KiB.)
