# Contributing

Genesis is a research codebase, not a prompt wrapper. Contributions should make
the architecture more capable, more measurable, or safer without replacing its
machine-native cognition with an external model or fixed responses.

## Read first

- [`AGENTS.md`](AGENTS.md) — architecture invariants and the no-hardcoding rule.
- [`SECURITY.md`](SECURITY.md) — runtime boundary and reporting rules.
- [`DEVLOG.md`](DEVLOG.md) — measured behavior and known gaps.
- [`docs/ARC-AGI-3.md`](docs/ARC-AGI-3.md) — the ARC evaluation boundary.

## Required checks

From a checkout with the documented system dependencies installed:

```bash
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test
ruff check
python3 -m pyflakes python/ genesis_client/ infrastructure/ world/ eval/ *.py scripts/*.py
python3 -m mypy python/ genesis_client/ infrastructure/ world/ eval/ --ignore-missing-imports
PYTHONPATH=python:. python3 -m pytest python/tests/ -q -o addopts=''
```

On a host without a C linker, source the helper first:

```bash
. ./scripts/cargo-env.sh
```

Do not weaken a repository check to make a change pass. If a check is wrong,
fix the check's boundary and explain why.

## Rules that matter most

- **No canned cognition.** Seeds and building blocks are acceptable; final
  thoughts, speech, plans, and benchmark behavior must be generated by the
  architecture.
- **No hidden benchmark shortcuts.** Do not read game internals, encode a
  game-specific solver, or bypass the readiness and scorecard contracts.
- **Fix root causes.** Prefer a small correct change over a broader workaround.
- **Respect persistent state.** The developmental record is not disposable;
  isolated tests and disposable daemons are required for experiments.
- **Match existing style.** Use the code's own abstractions, naming, error
  boundaries, and verification patterns.
- **Leave dead code dead.** Delete unused machinery rather than preserving a
  second path someone might accidentally trust.

## Pull requests

A useful PR includes:

1. the problem and intended invariant,
2. the smallest change that enforces it,
3. focused tests that fail without the change,
4. verification output,
5. and an explicit statement of what was *not* proven.
